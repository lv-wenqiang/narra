# 设计规格：横版 / 竖版双尺寸输出

日期：2026-09-04
状态：**已批准，待转实施计划**

## 1. 目标

一个 `--orientation` 选项，产出两种尺寸的成片：

| 档位 | 尺寸 | 用途 |
|---|---|---|
| `landscape`（默认） | **1920×1080** | 横屏平台 |
| `portrait` | **1080×1920** | 抖音 / 视频号 / Reels |

现有输出是 1280×720。**这个尺寸不再是产品尺寸**，降级为 `Canvas::BASE`——
所有版式常量当初就是在它上面手工调优的，它继续作为「缩放基准」与「测试基线」
存在于代码里，但不作为 `--orientation` 的可选值。

## 2. 核心策略：同一套版式，按宽度重新比例

9:16 不是 16:9 的等比缩放，但本项目的版式**大部分元素本来就是垂直居中的**
（Cover 容器、Intro 标题、字幕、Outro 组），唯一的绝对垂直锚点是 Cover 水印。
因此不需要两套版式常量，只需要：

- **长度量纲的常量** × `scale`，其中 `scale = 画布宽 / 1280`
- **垂直锚点**写成画布高度的比例
- **无量纲的常量**（帧数、比率、颜色、行高倍数）原样不动

`scale` 以**宽度**为基准而非高度或对角线：文字排版的约束是横向的（换行、
可读的字符密度）。以宽度为基准可以保证「元素占画布宽度的比例」在两档之间
恒定——1920 下字幕 120px、1080 下 67px，都是画布宽的 6.25%。

| | BASE 1280×720 | landscape 1920×1080 | portrait 1080×1920 |
|---|---|---|---|
| `scale` | 1.0 | 1.5 | 0.84375 |
| 字幕字号（短） | 80px | 120px | 67.5px |
| 占画布宽 | 6.25% | 6.25% | 6.25% |
| Outro logo | 216px | 324px | 182px |
| 占画布宽 | 16.875% | 16.875% | 16.875% |

**代价**：竖版上下会有较大留白。这是「同一套版式」的必然结果，是接受的取舍
——换取的是两档共用一套常量表，改一处版式不必想两遍。

## 3. 三个「碰巧同值」的陷阱

清点 `src/render/draw.rs` 的 78 个常量时发现三处：**在当前尺寸下两种算法给出
相同的数，换尺寸才分道扬镳**。它们不会编译失败、不会报错，只会让画面静默错位
——正是本项目一贯最警惕的失败形式。实施计划必须逐条覆盖。

### 陷阱 1：`COVER_CONTAINER_CENTER_Y = 360.0` 是写死的

Cover 的居中容器，语义是「垂直居中于画布」，即 `CANVAS_H / 2`。当前
`CANVAS_H = 720`，`720 / 2 = 360`，与写死的字面量**恰好相等**。

- 1920×1080 应为 540，写死值给 360 → 容器偏上 180px
- 1080×1920 应为 960，写死值给 360 → 容器偏上 600px

**修法**：改成 `CANVAS_H / 2.0`。旁边的 `CAPTION_CENTER_Y` 与
`INTRO_TITLE_CENTER_Y` 已经是这么写的，只有它掉了队。

### 陷阱 2：`OUTRO_LOGO_SIZE_PX` / `OUTRO_RING_RADIUS_STEP_PX` 按**高度**推导

两者现在都是 `CANVAS_H * 0.3`。在**任意 16:9 画布**上，`H = W × 0.5625`，于是
`H × 0.3 = W × 0.16875`——按高推导与按宽推导**给出完全相同的数**：

| | 按高 `H×0.3` | 按宽 `W×0.16875` |
|---|---|---|
| 1280×720 | 216 | 216 |
| 1920×1080 | 324 | 324 |
| **1080×1920** | **576** | **182** |

也就是说这个错误**在横版怎么改尺寸都测不出来**，只有竖版会暴露：576px 的 logo
占 1080 宽画布的 53%，而设计意图是 17%。

**修法**：改成按 `scale` 推导（`216 * scale`）。横版数值不变，竖版才正确。

### 陷阱 3：三个 `2000.0` 的「不换行哨兵」在 1920 下不再安全

`WATERMARK_MAX_WIDTH_PX`、`COVER_ROW_TEXT_MAX_WIDTH_PX`、
`OUTRO_TITLE_MAX_WIDTH_PX` 都是 `2000.0`，语义是「给一个远大于画布宽度的值以
避免意外换行」。在 1280 宽下它是画布的 1.56 倍，安全。

**在 1920 宽下它只比画布宽 4%**——一个长品牌名配上 1.5 倍放大的字号，真的可能
触发换行，而这是本次改动**会引入**的新缺陷。

**修法**：改成 `CANVAS_W * 2.0`，让「远大于画布宽」这个语义随画布走，而不是
指望一个字面量永远够大。

> **这是三个陷阱里唯一会改变 BASE 上常量数值的一处**（`2000.0` → `2560.0`），
> 因此值得对着第 6.1 节的逐字节门禁说明白：它**不会**破坏门禁。这个值的唯一
> 作用是喂给排版器当「最大宽度」，而放宽一个不曾被触发的上限不会改变任何一次
> 换行决策——BASE 下现有文案在 2000 时本来就不换行。门禁若真的红了，说明存在
> 一处「本来就在 2000 附近换行」的文案，那是**发现了一个既有缺陷**，不是重构
> 出了错，应当当场记账而不是把门禁调松。
>
> 另两个陷阱在 BASE 上数值不变：陷阱 1 的 `CANVAS_H / 2 = 360` 与写死值相等，
> 陷阱 2 的按宽推导在 16:9 下与按高推导同值（见上表）。

## 4. 架构

### 4.1 收敛画布尺寸的两个真相源（先决条件）

当前 `timeline::{WIDTH, HEIGHT, FPS}` 与 `draw::{CANVAS_W, CANVAS_H, FPS}`
**互不引用**，各写一份。`docs/follow-ups.md`（TTS 子系统第 3 条）早已记账：
「两边一旦不一致，结果是画面静默错位，而不是编译失败」。

本次必须先收敛，否则 `--orientation` 只会改到其中一边。收敛后销该条账。

### 4.2 `Canvas`

```rust
pub struct Canvas { pub w: u32, pub h: u32 }

impl Canvas {
    /// 版式常量的调优基准，也是测试基线（scale = 1.0）。不是产品尺寸。
    pub const BASE: Canvas = Canvas { w: 1280, h: 720 };
    pub const LANDSCAPE: Canvas = Canvas { w: 1920, h: 1080 };
    pub const PORTRAIT: Canvas = Canvas { w: 1080, h: 1920 };

    /// 长度量纲常量的缩放因子，以 BASE 的宽度为基准。
    pub fn scale(&self) -> f32 { self.w as f32 / Self::BASE.w as f32 }
}
```

### 4.3 `Metrics`：一次算好的版式表

`Painter::new(branding, canvas)` 在构造时把全部长度量纲常量按 `scale` 算好，
存进一个 `Metrics` 结构体；绘制时读 `self.m.caption_font_size` 等字段。

三个理由：

1. **缩放只算一次**，不在逐帧热路径上反复乘。
2. **常量表仍集中在一处**（`Metrics::for_canvas(canvas)`），可读性不比现在差
   ——它就是现在那张常量表，多了一个 `* scale`。
3. **可以脱离渲染直接断言**：`Metrics::for_canvas(Canvas::PORTRAIT)` 是纯函数，
   测试不必渲染整帧就能核对比例关系。第 6 节的竖版测试全部建在这上面。

### 4.4 常量分类

`src/render/draw.rs` 共 **78 个常量**（已核）。分五类处理：

| 类别 | 处理 |
|---|---|
| **长度量纲**（字号、边距、间距、描边宽、图标尺寸、**像素位移**） | `× scale` |
| **由画布宽推导**（`CANVAS_W * 0.8` 一族、水平中心） | 已正确，随 `CANVAS_W` 走 |
| **由画布高推导**（垂直中心、垂直锚点） | 陷阱 1、2 在此，见第 3 节 |
| **不换行哨兵**（三个 `2000.0`） | 陷阱 3，改成 `CANVAS_W * 2.0` |
| **无量纲**（帧数、比率、颜色、行高、字符阈值、`em` 字距） | 不动 |

**逐条分类是实施计划的第一项任务**，以 78 这个总数作校验和：每个常量必须被
显式归入某一类，五类之和等于 78，不允许「没想到它」的漏网。这里不预先给出
各类计数——那需要逐行判定，而判定过程本身就是那项任务要产出的东西。

**「像素位移」这一类特别容易漏**：`ENTRANCE_TRANSLATE_X_RANGE = [100.0, 0.0]`、
`ENTRANCE_LETTER_SPACING_RANGE = [8.0, 0.0]`、
`OUTRO_TITLE_TRANSLATE_Y_RANGE = [-50.0, 0.0]` 三者写在「动画」小节里，看起来
像动画参数，量纲却是**像素**，必须跟着缩放。不缩放的后果是竖版的入场位移相对
画面偏大、横版偏小。

### 4.5 不需要改动的部分

- **`src/render/text.rs`**：实现里没有任何画布尺寸假设（只有它自己的测试用到
  1280×720），排版层天然与画布无关。
- **`src/ffmpeg.rs` 的滤镜与命令行**：早已是 `scale={WIDTH}:{HEIGHT}`、
  `crop={WIDTH}:{HEIGHT}`、`-s {WIDTH}x{HEIGHT}`，参数化已就绪。只有**测试**里
  硬编码了 `1280x720`，要改成跟着 Canvas 走。
- **时间轴**：段落帧数（15 / 105 / `ceil((A+2)×30)` / 120）与分辨率无关。

## 5. CLI

```
--orientation landscape|portrait     # 默认 landscape
```

`render` 与 `debug-frames` 都加；环境变量 `ORIENTATION`；沿用既有的
`--flag > 环境变量 > 默认值` 三级兜底与「非空白才算数」语义。

**不做** `--size WxH`：任意宽高比会让版式失去可调优的基准，测试也从「两组确定
基准」退化成「任意尺寸下的不变量」，鉴别力显著下降。两档覆盖需求。

**不做** `--orientation both`：跑两次 `panda render` 复用同一份 TTS 产物即可，
要方便就在 `justfile` 加一条配方。

**BASE 不作为可选值**：它是调优基准与测试基线，不是产品尺寸。若将来真要 720p
输出，加一个枚举值是几行的事，届时再说。

## 6. 测试策略

`draw_tests.rs` 有 102 处 `Pixmap::new(1280, 720)`、60 个测试函数，是这个仓库
最贵的资产。策略是**把它们整体变成 BASE 基线，一个断言数值都不改**。

### 6.1 现有测试 → BASE 基线（scale = 1.0）

全部改成显式渲染在 `Canvas::BASE` 上，**断言数值一律保持原样**。它们由此获得
一个新职责：证明 `Metrics` 的推导在 `scale = 1.0` 时与手工调优的原值完全一致。

**硬门禁**：重构前后，在 BASE 上渲染同一帧必须**逐字节相同**。这是本次重构唯一
能拿到的「行为未变」证明，不能省。

### 6.2 新增竖版/横版测试：只断言比例不变量

不重复一遍逐像素坐标（那是 BASE 基线的职责，重复只会让改版式时要改三处），
而是断言跨尺寸成立的性质：

- **占宽比恒定**：同一元素的墨迹宽度 ÷ 画布宽，在三档下相等（±容差）
- **垂直居中**：Cover 容器 / Intro 标题 / 字幕 / Outro 组的中心在 `h/2`
- **Cover 水印**中心在 `0.8h`
- **不越界**：四段在两档下都不画到画布外
- **陷阱回归**：三个陷阱各有一条专门的测试（见 6.3）

### 6.3 三个陷阱的专项测试

每个陷阱都要有一条**在横版下也会红**的测试，否则等于没测：

| 陷阱 | 测试判据 |
|---|---|
| 1 · `COVER_CONTAINER_CENTER_Y` | 断言它等于 `h/2`，在 PORTRAIT 与 LANDSCAPE 下各验一次 |
| 2 · Outro logo 按高推导 | 断言 `logo 尺寸 / 画布宽` 三档相等——按高推导时 PORTRAIT 会红 |
| 3 · 不换行哨兵 | 断言 `max_width > 画布宽`，LANDSCAPE 下 `2000 < 1920 × 2` 才够 |

### 6.4 变异验证

沿用本仓库惯例：每条新测试写完后，拿变异（把生产代码改错一处）确认它真的变红。
至少覆盖：漏缩放某个长度常量、`scale` 用高度而非宽度、陷阱 1/2/3 各自的错误写法。

## 7. 性能

两档都是 **2.25× 于 BASE 的像素量**。

当前实测（`docs/ffmpeg-pipeline.md`）：「叠加+编码」约 142fps，远超 30fps 实时线。
按像素量线性外推约 63fps——**仍在实时线以上，但余量从 4.7× 降到 2.1×**。

**这是外推不是实测，实施计划必须实测确认**，并把数字写回
`docs/ffmpeg-pipeline.md`。若实测显著低于外推（例如编码不随像素线性），需要
重新评估是否降低默认 CRF 或调整 preset。

反预乘的 `alpha == 0` 快路径（已实测 3.89×）在更大画布上收益会同比放大。

**成片体积**约翻倍（当前 26.3s / 4.0MB）。

## 8. 附带影响

- **背景素材白捡一次质量提升**：`public/video/0.mp4` 本身是 **1920×1080 AV1**，
  现在被降采样到 1280×720 白白丢掉细节；输出改成 1080p 后是 1:1 映射，不再缩放。
  竖版则会按 cover 语义中心裁切，只保留中间约 31% 宽——**这是有意保留的行为**，
  想要好的竖版取景就给竖版素材（`--bg` 本来就支持）。不做模糊填充（YAGNI）。
- **`docs/follow-ups.md` 要订正一条**：「`assets/logo.png` 换成 256px 预缩版能省
  1.3MB」现在**确定是错的**——1080p 横版的片尾 logo 需要 324px，256px 不够。
  内嵌原图 2048² 在两档下都够用（324 / 182），保持不变。
- **规格 §8 要大改**：各段视觉规格里的绝对像素值要改写成「BASE 值 + 比例关系」。
- **`docs/ffmpeg-pipeline.md`** 里的分辨率相关读数要更新（帧数、时长、音频各项
  实测结论不受影响，那些与分辨率无关）。

## 9. 分阶段

拆成两份实施计划，A 完成时有一个可独立验证的中间态：

| | 内容 | 完成标志 |
|---|---|---|
| **A** | 收敛画布真相源；引入 `Canvas` / `Metrics`；78 个常量逐条分类改造；修掉三个陷阱；现有测试改成 BASE 基线 | **BASE 上渲染逐字节不变**；不引入任何新尺寸 |
| **B** | 加 LANDSCAPE(1920×1080) 与 PORTRAIT(1080×1920)；CLI `--orientation`；比例不变量测试；实测吞吐并写回文档 | 两档成片可播、比例正确、吞吐实测 |

A 是纯重构且有逐字节门禁，风险可控；B 建在一个已经证明「行为未变」的地基上。

## 10. 风险

- **动的是这个仓库最贵资产的地基**（`draw.rs` + `draw_tests.rs`）。缓解手段是
  A 阶段的逐字节门禁——它把「重构」与「换尺寸」这两件事彻底分开，任何一处漏改
  都会在 A 阶段被抓住，而不是混在竖版的视觉差异里。
- **陷阱式缺陷的性质是静默**。三个已知陷阱各有专项测试；但清点是人工做的，
  可能还有第四个。缓解手段：A 阶段除逐字节门禁外，再加一条「在一个**非
  16:9、非 BASE** 的临时尺寸下渲染不 panic、不越界」的测试——它能撞出那些
  「在 16:9 下碰巧同值」的漏网之鱼。
- **性能余量下降**（4.7× → 2.1×）。实测若不达预期，退路是把默认档降回
  1280×720 或调 x264 preset，两者都不影响本设计的结构。
